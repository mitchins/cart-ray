# Test-only OrderConfirmed queue subscriber

This optional consumer verifies a versioned, HMAC-authenticated source hint and sends only its outbox ID through a private service binding to the existing Reviews intake. That intake re-reads the confirmed CartRay order and commits its independent receipt and held intent atomically; this queue consumer never updates the commerce outbox or authorizes email. The existing activation fence continues to exclude pre-activation events. A queue acknowledgement follows the durable intake response; a crash before acknowledgement results in a safe repeat. Provider errors, missing configuration, invalid responses and timeouts retry. Malformed messages are discarded without a database call. Well-formed messages with a signature or scope mismatch retry to the bounded dead-letter queue so a key or installation mismatch cannot silently lose a legitimate order. The private producer boundary, finite retries and DLQ monitoring must prevent untrusted flooding; operators must reconcile DLQ messages after correcting configuration.

The message has exactly `version`, `issuer`, `installation`, `store`, `environment`, `outbox_id`, and `signature`. `version` is 1; the signature is hex HMAC-SHA256 over the UTF-8 JSON array `["cartray-reviews-order-confirmed-v1", issuer, installation, store, environment, outbox_id]`. The event key is a distinct 32-byte hex secret, never the service token. Values for `SOURCE_ISSUER`, `SOURCE_INSTALLATION`, `SOURCE_STORE` and `REVIEWS_ENVIRONMENT` must match on both sides. Only `REVIEWS_ENVIRONMENT=test` and `REVIEWS_ORDER_SUBSCRIBER=test` enable execution. Provision a finite retry queue and DLQ and a private `REVIEWS_API` service binding.

This is **not** a producer, subscription, source attestation, or production installation: configured store, installation and database identities remain operator assertions. Do not activate it against a real store until the actual Worker/version and D1 bindings, Stripe account, mapping and issuer have been independently verified and the attestation is enforced by the runtime. Test-only traffic only; no sending, scheduling, or new checkout dependency.

For the synthetic Acorn checkout-permission integration, provision a separate private Worker with `modules/reviews/consent/purchase_evidence.mjs` as its entrypoint and the attested commerce and context D1 bindings described by the test authority. Bind it to this subscriber as `PURCHASE_EVIDENCE`, and set `AUTOMATION_EVIDENCE_ENABLED=test` plus the same distinct, high-entropy `AUTOMATION_EVIDENCE_TOKEN` as a secret in both Workers. Provision distinct `REVIEWS_RECIPIENT_EVIDENCE_SECRET` and `REVIEWS_CONSENT_SECRET` secrets on the evidence and Reviews Workers. Never expose this Worker as a public route. If the feature is disabled or omitted, the original intake path is unchanged.

After a durable accepted intake, the optional evidence Worker rechecks source attestation, confirmed purchase and Stripe account and records the checkout grant and confirmed purchase contact. Absence of a grant is acknowledged with no evidence; an unavailable dependency or invalid receipt retries the queue message, whose intake and evidence writes are idempotent. Pre-activation and late events do not invoke evidence. Intake and evidence have separate bounded deadlines. An accepted grant creates no invitation or email. The Stripe contact is purchase contact evidence, not proof that the purchaser controls the mailbox. Receipt-only mode and production sending are not implemented here.
