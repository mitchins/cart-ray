# Test-only attested outbox producer

This producer is disabled unless `REVIEWS_ENVIRONMENT=test` and `REVIEWS_SOURCE_PRODUCER=test`. It needs private service bindings `SOURCE_API` and `REVIEWS_API`, `COMMERCE_DB`, an `EVENT_QUEUE` producer binding, a `CF_VERSION_METADATA` binding, and distinct secrets `CF_READ_TOKEN`, `SOURCE_IDENTITY_TOKEN`, `REVIEWS_ACTIVATION_TOKEN`, `TRIGGER_TOKEN`, and a 32-byte hex `SOURCE_EVENT_KEY`. Set the scoped Cloudflare account, Worker names, database ID, Stripe account ID, store, issuer, installation, catalogue version, exact Reviews mapping SHA-256, and numeric activation policy variables shown in `worker.mjs`. The read token needs the control-plane read permissions for the four Workers and both queues. Configure distinct EVENT_QUEUE_NAME / EVENT_QUEUE_ID and DEAD_LETTER_QUEUE_NAME / DEAD_LETTER_QUEUE_ID. The source queue must be unpaused, have exactly one expected Worker consumer, 1–10 retries and the configured DLQ; the DLQ must have no automatic consumer. Any mismatch fails closed before checkpointing or sending. No email, recipient or Reviews collection binding is used.

Before each relay the producer checks current Cloudflare deployments and exact version settings for the source, producer and Reviews Workers. It rejects traffic splits, source/producer/Reviews D1 binding mismatches, wrong service binding targets, source identity, store, test mode, catalogue or exact mapping mismatches. The source identity endpoint uses the source Worker's own Stripe test credential to fetch the account and reports its own version metadata; this endpoint is authenticated and disabled unless `CARTRAY_REVIEWS_SOURCE=test` and a separate identity token are configured. The source Worker also needs a version metadata binding and private `REVIEWS_SOURCE_TRIGGER` service binding. Configure `CARTRAY_REVIEWS_PRODUCER=test` and matching trigger token only for a qualified test deployment.

The producer asks the existing idempotent activation endpoint for its primary-session no-backfill watermark. A dedicated immutable installation-scoped checkpoint is created at that watermark. At most 20 confirmed outbox IDs are enqueued per run, then the checkpoint advances by compare-and-set only after queue acceptance. A crash after send may duplicate a hint; the downstream Reviews transaction deduplicates it. The normal webhook wakes this producer asynchronously after settlement; the existing scheduled reconciliation wakes it for recovery. Neither missing bindings nor a failing wakeup change checkout responses. The source producer must also have a bounded scheduled trigger for backlog recovery.

This is an unqualified test implementation: configuration, Cloudflare control-plane credentials, resource bindings, topology, version changes, timeouts and end-to-end behavior must be validated under Workerd and hosted sandbox before enabling it. A control-plane check cannot make a deployment change and an in-flight send atomic; deployment changes must quiesce and revalidate this source before new events are accepted. Production, arbitrary backfill and outgoing invitations remain disabled.

A private authenticated `POST /attest-purchase` can issue a nonce-bound, 30-second HMAC proof for the separately deployed purchaser authority. It verifies the active authority version and its actual `COMMERCE_DB`, `CONTEXT_DB`, `SOURCE_IDENTITY`, `CHECKOUT`, `ATTESTOR`, `REVIEWS_API`, and version-metadata bindings against the control plane. The request is exactly `{authority_version, nonce}`; the version is only a hint. The response is `{proof, signature}` where `proof` is the compact JSON array `["cartray-reviews-purchase-attestation-v1", store, "test", installation, source_database_id, authority_context_database_id, stripe_account_id, catalogue_version, mapping_sha256, source_worker_version, reviews_worker_version, producer_worker_version, authority_worker_version, nonce, issued_unix_seconds, expires_unix_seconds]`; the signature is lowercase hex HMAC-SHA256 over the UTF-8 compact JSON array using the distinct 32-byte hex `PURCHASE_ATTESTATION_KEY`. The caller must verify its own expected scope, nonce, time, and signature. This RPC needs the separate `PURCHASE_ATTESTATION_TOKEN`, `PURCHASE_ATTESTATION_KEY`, `AUTHORITY_WORKER`, and `AUTHORITY_CONTEXT_DB_ID` configuration. It is not itself purchaser or recipient proof.

## Preparing a disposable hosted topology

`uv run --locked python modules/reviews/tools/prepare_hosted_source_topology.py --resources /path/to/nonsecret-resources.json --output /new/private/config-directory` generates four explicit test-only Wrangler configurations and validates that Reviews D1, commerce D1, the event queue and DLQ are distinct. The descriptor shape and a safe synthetic example are in `modules/reviews/tests/test_hosted_source_topology.py::config`. Set `stripe_account_id`, resource IDs, catalogue version, subject mapping and storefront origin to the independently verified disposable installation. The generator creates no cloud resources, reads no credentials, and does not verify deployment bindings; the runtime attestor still performs those checks. The generated source Worker is a separate test Worker, not the existing checkout Worker.

The source config must be built with `CARTRAY_CATALOGUE_PROFILE=acorn-stripe-test` and a fresh private preflight lock, using locked `uv`/pywrangler. Provision the actual matching test-only secrets through a private secrets file or the Wrangler secret interface; never put them in TOML, shell history, logs or a public receipt. The source needs the existing checkout signing and Stripe test secrets plus `CARTRAY_REVIEWS_IDENTITY_TOKEN` and `CARTRAY_REVIEWS_TRIGGER_TOKEN`. Reviews needs distinct test settlement, admin, invitation, reviewer, activation and ingress credentials. The consumer needs the matching event key and ingress token; the producer needs the matching event key, activation, source identity, trigger and narrowly scoped Cloudflare read token. The producer's control-plane token must read the named Workers and both queues. If testing purchase attestation, provision the separate proof token/key and context database as documented above.

Deploy the isolated resources only after recording the original checkout deployment and a rollback plan. Private service dependencies are cyclic: provision nonfunctional, private test Worker names before deploying the final source, Reviews, consumer and producer versions; do not enable or invoke relay until all final versions and bindings are present. Apply migration `0005_reviews_subscriber.sql` to the intended synthetic commerce D1 only after confirming its identity; apply Reviews migrations to its separate disposable D1. Inspect active deployment versions, actual D1/service/queue bindings, queue retry and DLQ configuration, source account identity and the pre-existing outbox watermark before an activation attempt. Create a new sandbox purchase through the clone and verify the pre-activation event remains fenced, the new Reviews receipt is unique, and the global outbox delivery column remains untouched. Exercise mismatches, retries and subscriber unavailability before accepting evidence.

Cleanup targets are only the four explicitly named disposable test Workers, the disposable Reviews database, and the explicitly named test event queue/DLQ. Never delete or reset the pre-existing checkout D1 or the original Worker. After verifying queue contents and capturing sanitized receipts, remove only the named disposable resources with the corresponding Wrangler deletion commands and remove locally generated private files. Keep the preflight lock and non-secret receipt needed to reproduce the qualification, subject to the operator's retention policy.
