# Reviews moderation console (test only)

A small, independent staff surface for the Reviews pending and published lists, revision and audit histories, approval/rejection and revision-bound withdrawal. It requires the separately developed staff operations API and is not deployed or enabled by installing Reviews. To test, serve this directory under an authenticated, same-origin test gateway that forwards `/reviews-admin/v1/` to the Reviews Worker in explicit test collection mode and injects a verified staff assertion at the trusted gateway. The gateway must protect the HTML and API with the same independently authenticated staff policy. No assertion, administrator token or secret is entered into or stored by the page. Do not expose this experimental UI publicly or use it with production data.

The pending API currently provides a subject reference rather than an approved product name; published results show the approved name when available. Lists are cursor-paginated, not snapshot-consistent under concurrent edits. History is ordered by opaque IDs, not by revision time; audit timestamps are shown only when supplied by the API. Published native reviews support one staff reply with immutable revisions; a withdrawn reply cannot currently be replaced. A failed or uncertain reply request retains its exact payload and idempotency key for a safe same-request retry. The delivery investigation list requires the independent `reviews:operations` permission and is read-only: neither resend nor provider-outcome reconciliation is available here. The Access-only purchase-mode prerequisite, live identity-provider qualification, deployment policy and operator permissions remain gates. This console is a development slice, not a complete merchant product.

Subject administrators can set the customer-facing invitation name of an existing subject by its reference. This does not create a subject, change the storefront catalogue, or set review eligibility. The API is last-write-wins and provides no readback, revision history or audit for this setting; concurrent administrators can overwrite one another. A lost response is treated as uncertain and the form is locked until the current value has been verified through an operator. Full managed settings and audited, concurrency-safe changes remain release work.

For a local browser qualification against the actual Reviews Workerd/D1 path, install the repository's locked development dependencies and ensure `lsof` is available, then run `PYTHONPATH=modules/reviews/src .venv/bin/python modules/reviews/console/tests/workerd_gateway.py`. Pass `--operations` for delivery permission and `--subjects` for subject administration; without them the respective operations must be denied. It creates disposable local D1, seeds one synthetic pending review and one uncertain synthetic delivery, starts the Worker in test-only signed-staff mode, and serves the console at `http://127.0.0.1:48974/`. Before sending synthetic credentials, it checks that the listener belongs to its own Worker process group and responds with an unpredictable marker from its disposable D1. The loopback gateway injects a generated synthetic staff assertion server-side; it does not implement or qualify a real staff login. `/__test/summary` shows the synthetic public summary. Stop it with Ctrl-C to delete the local test database and stop its Worker. Never run the test gateway with real data or expose it outside loopback.
