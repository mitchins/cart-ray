# SMTP2GO activity evidence (test only)

The initial sender attaches SMTP2GO's returned `email_id` to its existing delivery outcome. The Reviews D1 transaction stores that identity against the acquisition, generation and delivery identity when acceptance is committed. A conflicting ID is rejected, including on replay. Provider acceptance activates an invitation under the existing publication and suppression rules; it does **not** mean the mailbox accepted delivery.

This private, explicitly enabled Worker looks up a previously recorded provider email ID through SMTP2GO [`/v3/activity/search`](https://developers.smtp2go.com/reference/search-activity), using an independently scoped activity-read key and a distinct bearer token. It verifies every result's email ID, event type and timestamp, rejects partial/paginated, malformed or mismatched responses, and appends idempotent observations without storing addresses or provider response text. Processed, delivered, rejected, soft-bounced and hard-bounced events remain distinct; observations do not mutate the invitation generation or authorize a new send. An empty lookup, provider outage, truncated history or missing ID is unknown, not proof of non-delivery. The operator must investigate unknown outcomes; this adapter never resends.

Activity can lag and the provider may expire its history ([SMTP2GO activity guide](https://developers.smtp2go.com/docs/view-account-activity)). If the send response was lost before its provider ID was persisted, `/discover` searches a bounded recipient/time window using the private confirmed-purchase recipient and requires an exact `X-Reviews-Delivery-Identity` match across every page. A single matching provider ID is recorded as discovery evidence for an operator. It does not invent an exact acceptance time, activate an invitation or authorize resend. Missing, truncated, expired or ambiguous evidence remains unknown. A read-only probe against a prior synthetic message confirmed the custom headers and processed/delivered activity shape using the real provider and disposable local SQLite. The processed event omitted a recipient field but contained the matching `to` address. This did not qualify the adapter under hosted Workerd; hosted qualification and permissioned operational reconciliation remain required.

`REVIEWS_ENVIRONMENT=test` and `SMTP2GO_RECONCILIATION=test` are both required, together with `REVIEWS_STORE`, `REVIEWS_DB`, a distinct `RECONCILIATION_TOKEN` and `SMTP2GO_ACTIVITY_KEY`. The `/reconcile` and `/discover` routes accept only the acquisition, generation and delivery IDs over that private authentication boundary. `/discover` additionally requires the existing private `PURCHASE_EVIDENCE` binding, distinct `AUTOMATION_RECIPIENT_TOKEN`, and exact `APPROVED_TEST_EMAIL` allowlist. No public route, schedule or provider operation is enabled by default. Do not deploy the worker as a production administrative boundary.

For recovery delivery, the optional `smtp2go-recovery` adapter implements the same single approved test sender and recipient restriction. Set the recovery dispatcher's `SYNTHETIC_MAIL_PROVIDER=smtp2go`, provide a private `SMTP2GO_MAIL` service binding and a distinct `SMTP2GO_MAIL_TOKEN` shared only with that service. The adapter requires `REVIEWS_ENVIRONMENT=test` and `SMTP2GO_RECOVERY_MODE=test`. It returns the provider email ID only after a successful SMTP2GO response. The existing dispatcher's claimed-before-send and uncertain-on-error behavior is unchanged. Generic MAIL remains supported without a provider ID and cannot claim SMTP2GO activity evidence.
