## Delivery plan and decision gates

1. **R0: complete inventory and contract.** Identify production and its source revision/capture time; inventory effective plugin settings and writer paths, comment types/statuses, parent edges, subject aliases, metadata, media, active workflows, external dependencies, existing public page metadata/markup/anchors and actual consumer journeys. Capture source-backed counts and per-feature evidence, distinguish used/configured/unknown, document dispositions and one-sender ownership. Verify the widget rights and Trustpilot pending jobs with the appropriate owner. Define a versioned, approved-public snapshot contract, privacy allowlist, validation, subject/aggregate semantics, reproducibility, and failure behaviour. R0 is read-only; never submit a review, send mail or modify WordPress.
2. **R1: opt-in foundation, parallel only where independent.** Under `modules/reviews/**`, implement a separately installable/deployable module and safe versioned snapshot/projection contract with synthetic fixtures and module-absent isolation tests. No default bindings, routes, resources, scheduled work, core subscriber ledger, checkout adapter, email, live collection or production activation. Review interfaces before coupling an importer or renderer. Pin runtime and prove actual Workerd/D1 compatibility when applicable. An absent module leaves core unchanged.
3. **R2: migration rehearsal and static presentation.** Produce restricted export/import and repeatable reconciliation, explicit mappings and exception reports. Verify all historical media including the four separate testimonial videos; keep spam private. Test with real source data in an authorised, isolated staging workflow as well as synthetic edge cases. Publish only an approved pinned public snapshot; build EP Astro HTML and matching product JSON-LD from it, preserve legacy anchors and existing external surfaces. Compare every record and render in a real staging browser. Imports emit no notifications. Use existing EP ownership, release and review processes; no automatic production publication.
4. **R3: collection and moderation.** After pre-implementation review, develop independently gated guest submissions, verification, moderation, revisions and retained enabled engagement features. Enable only after security and staging qualification, and a decision on the maximum withdrawal stale window and the tested removal path for static HTML, JSON-LD and media, including failed builds and emergency takedown. No requirement for an account or purchase to submit a general review.
5. **R4: purchase and invitations.** Separately implement optional subscriber delivery, verified purchase context, purpose-specific opt-in bound to recipient and order, suppression, qualified provider and due-time scheduling. Unknown consent means no invitation. Start with dry run and approved test mailbox; Woo owns existing purchase cohorts and Trustpilot pending jobs until explicit cutover. No temporary Woo adapter by default and no historical backfill by default.
6. **R5: cutover and retirement qualification.** Reconcile final changes, freeze only relevant writers when authorised, assign each pending send one owner, rehearse rollback including native-write deltas, and obtain separate production approval. The 15 fulfilment workflows and historical preference links remain on their own retirement ledger; a Reviews module does not retire WordPress.

R0 deliverables are a restricted consistent source bundle and media manifest; sanitized inventory and counts by status, type, subject, rating and parent; field dispositions; source-to-subject and relationship mappings; a feature and behaviour parity matrix with evidence; a writer/invitation and workflow-retirement ledger; public metadata, layout and anchor fixtures; and a versioned snapshot contract. Include plugin custom tables, taxonomies, configuration, relevant post/comment metadata, non-review contribution types, attachments, preferences, suppressions and legacy preference-token compatibility, across all states. Record used/configured/unknown separately from operational/historical/retired. Each enabled-but-unused capability needs a supported configuration mapping or explicit owner-approved retirement; archiving its data alone is not a disposition for the capability.

Before importer/renderer coupling, the snapshot contract must specify schema/version and hash validation, trusted origin or immutable artifact, environment separation, public allowlist, stable subject/review identities, legacy anchors, original dates, approved revisions, verification provenance, scoped summaries, and deterministic failure and freshness behaviour. Test private-field canaries in HTML, JSON and JSON-LD. Browser refresh must not silently alter the subject/source mixture or contradict static structured-data semantics.

Each implementation slice receives an independent GPT-6.1-Sol adversarial review before implementation and on its final diff, focused and full tests, Workerd/D1 integration checks, lint/build, required Sonar/secret-scan gates, and a completed final-head GitHub review. Record source identities, test results, known gaps and reviewer verdict. Preserve unrelated worktree changes. Automated production refresh, release approval and publication delay remain later decisions.

Queue, Durable Object and provider qualification belong to the slices that introduce them; explicitly record deferred gates and do not make those components prerequisites for the R1 snapshot foundation.

It also returned 6,975 order notes, which are not review content. The installed source also registers both authenticated and unauthenticated vote handlers when voting is enabled; metadata exists on six approved reviews. Existing votes warrant migration of the meaningful totals, not replication of the plugin's cookie or voter implementation. Further confirm effective settings and visible journeys without making submissions.

User direction: replace the actual use case and needed functionality, not legacy implementation oddities. Keep capability decisions explicit, but avoid building unused plugin machinery by default. An unsupported populated source field must be reconciled and given an appropriate documented disposition; preserving it in an archive does not imply rebuilding a legacy user interface.

A minimal pure-Python snapshot validation foundation is being developed in `modules/reviews`; it is not the complete R1 runtime or migration. The pre-implementation GPT-6.1-Sol review supported this bounded scope and requested strict field validation, provenance, scoped aggregates, graph and anchor checks, and independently approved pinned bytes.
