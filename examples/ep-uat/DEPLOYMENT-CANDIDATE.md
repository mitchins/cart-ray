# Effective Policy deployment candidate — not authorised for deployment

This is a handoff candidate informed by the public-catalogue and local sandbox tests. It is not a production architecture approval or evidence that the currently generated UAT audit pages are suitable for publication.

- Keep the existing EP Astro/static site and JavaScript site Worker. Give the separate CartRay Python Worker explicit private service bindings, account-owned configuration and its own merchant installation. Reviews remains an optional independently configured Worker. The shop and canonical product URLs stay with whichever storefront owns them; the UAT `/products/woo-.../` routes are not claims about live URLs.
- Route only an agreed, narrowly scoped same-origin commerce API prefix from the site Worker to CartRay and a separately scoped public Reviews prefix to Reviews. Preserve explicit method/path allowlists and reject unknown routes. Do not forward administrative routes or internal secrets to browser code. Before applying any route, evaluate overlapping live routes and ownership. Cloudflare evaluates the most specific matching route, and same-zone Worker-to-Worker calls to routed Workers require service bindings rather than assuming ordinary `fetch()` resolves: [Workers routes](https://developers.cloudflare.com/workers/configuration/routing/routes/), [Worker-to-Worker communication](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
- Same-origin routing removes the need to expose broad cross-origin access for site requests; it does not replace authentication, CSRF checks or origin validation. Define purchaser cookies by their actual authority, path and lifetime. Never treat an arbitrary browser-provided Checkout Session ID, email or product price as payment or entitlement authority. Check Stripe redirect/return behavior and real account branding for the EP account in an isolated test environment.
- Treat review capabilities as sensitive. Exclude them from cache keys, access logs and referrer leakage; preserve existing scoped capability and revocation behavior. Do not inject historical reviews or real customer invitations into this UAT. Configure explicitly approved subject mappings before presenting product reviews.
- Download delivery needs a supported server-side entitlement service bound to confirmed order and offer identities; this branch's loopback SQLite/dummy-file harness is not that service. Approve the real delivery mapping, asset handling, authenticated access and recovery before any paid delivery. The shared dummy payload and test Dropbox transfer do not resolve production fulfilment references.
- Serve approved public catalogue assets statically; retain versioned review-publication and withdrawal controls for HTML, structured data, API and media. Qualify actual EP storefront/CDN invalidation and operational costs; local UAT timings are not network/CDN budgets. Keep checkout usable when optional Reviews services are unavailable, while acknowledging a shared D1 outage can affect all services bound to it.
- Before any route, DNS, live payment, collection or fulfilment change, separately approve catalogue visibility, canonical mappings, EP Stripe merchant account, prices and entitlements, data/privacy, Reviews publishing and withdrawal, production observability, rollback and legacy writer ownership. Final WordPress or AutomateWoo retirement remains a distinct later decision. No such activation is authorised here.

The remaining implementation gap is a supported generic merchant storefront integration using the existing connected CartRay/GEL build and installer. The UAT-specific static builder and local test server on this branch demonstrate data and behavior; they do not replace that integration.
